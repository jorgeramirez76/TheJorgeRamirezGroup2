## Decisions

- 2026-07-03 — Source root is `crm/src/` (not `crm/server/src/` as written in a few places in `MASTER_BUILD_PLAN.md`, e.g. §6.1/§7/§9). Phase 1 scaffolding (`package.json`, `tsconfig.json`, `tests/`) was already in place using `crm/src/...` before schema/API code was written, so that layout was kept as the single source root for the whole `crm/server` process rather than introducing a redundant nested `server/` folder. All future phases should keep placing code under `crm/src/<area>/` (e.g. `crm/src/channels/imessage.ts`, `crm/src/ai/`, `crm/src/video/`) instead of `crm/server/src/...`.

- 2026-07-03 — Phase 2 (iMessage/BlueBubbles): the driver lives at `crm/src/channels/bluebubbles.ts` (not `imessage.ts` as named in §6.1) since it's specifically the BlueBubbles implementation of the `Channel` interface (`crm/src/channels/types.ts`) — a future `imessage-applescript` fallback driver (§6.1) would also implement `Channel` and could reasonably own the `imessage.ts` name once it exists.

- 2026-07-03 — `BLUEBUBBLES_WEBHOOK_SECRET` (in `.env.example`) is reserved but not enforced by `/webhooks/bluebubbles`. BlueBubbles has no built-in mechanism to sign or authenticate its outgoing webhook requests (no shared-secret header/param it will attach), and the endpoint is architecturally localhost-only (`CRM_HOST=127.0.0.1`, no tunnel path exposes it per §4/§10). If BlueBubbles ever runs on a separate host, revisit this — e.g. an nginx/Caddy reverse proxy in front that injects/checks the secret.

- 2026-07-03 — The send gate's "per-lead daily cap" (§6.3, §12) is implemented per **contact**, not per lead row. `messages` keys off `contact_id`, not `lead_id` (a contact can have both a buyer and seller lead), so the cap counts a contact's total outbound messages/day across all their leads and channels — the practical equivalent given the schema, and the safer reading of the compliance intent (don't over-text a person, regardless of how many pipeline entries they have).

- 2026-07-03 — Quiet-hours "next allowed window" math (`crm/src/sendgate/quiet-hours.ts`) computes the target-timezone UTC offset at the current instant and assumes it holds through the next occurrence of the window start. This is exact except on the ~2 days/year a DST transition falls between `now` and that next start, where it can be off by up to an hour — acceptable for v1; revisit with a proper tz library (e.g. `@js-temporal` or `date-fns-tz`) if that edge case ever matters in practice.

- 2026-07-03 — The STOP/opt-out confirmation (`crm/src/sendgate/optout.ts`) is inserted as a `messages` row with `status: 'queued'`, not actually dispatched through the `Channel`. There is no outbound dispatch/worker loop yet (that arrives with the workflow engine in Phase 5) — Phase 2's job is to prove the confirmation is queued exactly once per opt-out, which the tests do. Whatever picks up `queued` messages later must send this row through the normal send gate like any other outbound message.

- 2026-07-03 — Fixed two latent Phase 1 build bugs, surfaced only once the Phase 2 launchd service actually tried to run the compiled output on real hardware (`npm run dev`/tests never exercised `dist/`): (1) `package.json`'s `start` script and the launchd plist pointed at `dist/index.js`, but `tsconfig.json`'s `rootDir: "."` + `include` of both `src/**` and `tests/**` means `tsc` emits to `dist/src/index.js` — both now point there. (2) `src/db/migrate.ts` reads `migrations/0001_initial.sql` via `readFileSync` at a path relative to its own compiled location, but `tsc` doesn't copy non-`.ts` assets — `npm run build` now also copies `src/db/migrations/*.sql` into `dist/src/db/migrations/`. Verified end-to-end on Jorge's Mac Studio: `launchctl list` shows the service running, `/healthz` returns ok, and BlueBubbles' real `/api/v1/ping` succeeds with the configured password.

- 2026-07-04 — Live end-to-end webhook verification on Jorge's Mac Studio surfaced three real-world BlueBubbles gotchas, none of which are code bugs in this repo but all of which anyone repeating `crm/SETUP.md` will hit:
  1. **No webhook exists until you add one.** A fresh BlueBubbles install has zero registered webhooks (`GET /api/v1/webhook` returns `[]`) even after following the app's own onboarding — it must be added explicitly, either via the Server app's **API & Webhooks → Manage → Add Webhook** UI or `POST /api/v1/webhook`. `SETUP.md` §3 now calls this out as its own explicit sub-step, not folded into "configure BlueBubbles."
  2. **Use `127.0.0.1`, never `localhost`, in the webhook URL.** On this Mac `localhost` resolves to `::1` first; the CRM server binds only to IPv4 (`CRM_HOST=127.0.0.1`), so BlueBubbles' HTTP client fails the connection outright (logged as `[WebhookService] Failed to dispatch "new-message" event... Status Text: undefined`) instead of falling back to IPv4 the way `curl` does. `SETUP.md` now specifies the webhook URL as `http://127.0.0.1:4820/webhooks/bluebubbles` explicitly.
  3. **BlueBubbles' new-message detection appears to track a "since server start" cursor.** Messages that arrive *before* a BlueBubbles Server restart are never retroactively dispatched as `new-message` events after that restart, even though they're visible in Messages.app and counted in BlueBubbles' own dashboard stats. Only messages arriving *after* a given server session started got webhook-dispatched in testing. Practical implication: if you restart BlueBubbles Server (e.g. via **Debug Actions → Restart via Terminal**) while messages are queued/unprocessed, don't expect them to surface after the fact — send a fresh test message post-restart to verify.
  4. Without the **Private API** (requires SIP disabled via Recovery Mode — a real security trade-off, not attempted here), new-message detection is not the "<2s" instant target in §6.1 — it runs on some internal polling cadence instead of FSEvents-driven push. Functionally correct (proven: a post-restart test message was detected, webhook-dispatched, and landed in `messages` with a correctly-created `needs-review` shell contact), just not the target latency. Revisit enabling Private API/SIP-disable as a Jorge decision if instant response time becomes important before Phase 4's AI engine ships.

## Phase 3 (Gmail channel)

- 2026-07-04 — The Gmail SDK layer is its own thin interface, `GmailApiClient` (`crm/src/channels/gmail-client.ts`: `getProfile`/`listHistory`/`getMessage`/`sendRaw`), rather than passing the generated `googleapis` client straight into `GmailChannel`/the poller/`sendgate`. Tests exercise an in-memory `FakeGmailClient` (`tests/helpers/fake-gmail-client.ts`) against this interface instead of mocking HTTP calls into the generated SDK, which would mean asserting against `googleapis`' internals rather than this repo's own code. The real driver (`createGoogleGmailClient`) is a thin wrapper with no logic of its own to test beyond what the fake already proves at the call-site level.

- 2026-07-04 — Use `google.auth.OAuth2` (from the `googleapis` package itself) rather than importing the `google-auth-library` package directly. `googleapis` bundles its own internal copy of `google-auth-library`; installing it again at the top level produces two structurally-identical-but-nominally-different `OAuth2Client` classes (private fields make TS classes nominal, not structural) that fail to type-check against each other. `google.auth.OAuth2` sidesteps this entirely and needs no extra dependency.

- 2026-07-04 — The live Gmail history-poll cursor persists in `settings.gmail_history_id` (via the existing `settings` table/store), not in `.env`'s `GMAIL_HISTORY_ID` — mirroring how `imessage_health` already lives in `settings` rather than a file. This is what makes "cursor resume after restart" actually true: every `pollGmailInbox` call re-reads the cursor from the db, so a process restart (or, in tests, a fresh `drizzle()` handle over the same sqlite connection) picks up exactly where the last *persisted* poll left off. `npm run setup:gmail` still writes an initial `GMAIL_HISTORY_ID` value into `.env` for human debugging/reference, but nothing at runtime reads it — the first live poll seeds `settings.gmail_history_id` from a fresh `users.getProfile` call regardless. One related gotcha this forced: `DEFAULT_SETTINGS` cannot default this key to a bare `null` — drizzle-orm inserts a literal SQL `NULL` (not the JSON string `"null"`) for a top-level `null` value on a `mode:'json'` column, which trips the `settings.value NOT NULL` constraint. The key is simply omitted from `DEFAULT_SETTINGS`; `getSettings()` returns `undefined` for it until the poller's first run, which every call site already treats the same as `null`.

- 2026-07-04 — RFC 2822 `In-Reply-To`/`References` threading uses only the immediate parent message's `Message-ID` header (fetched on demand via `client.getMessage` right before composing a reply), not the full ancestor chain. The schema (§5, LOCKED) has no column for RFC `Message-ID` headers — only Gmail's own opaque message `id` (stored as `messages.external_id`) and `threadId` (stored as `messages.thread_key`). Gmail's `threadId` is what actually keeps the conversation grouped in Gmail's own UI; `In-Reply-To`/`References` are the RFC-compliance nice-to-have on top of that, and a single-parent reference is a reasonable approximation without a schema change.

- 2026-07-04 — Campaign (non-1:1) email throttling/dedup state (`email_campaign_state: {lastSentAt, countByDate}`) lives in `settings`, not as a new column on `messages`, since §5's schema is LOCKED and has no "is this a campaign send" flag to query against. `evaluateSendGate` reads this state (given `isCampaign: true`) the same way it already reads `imessage_health`; `sendCampaignEmail` is the only writer. Regular 1:1 sends (`sendOutboundEmail`) never touch this state and never get the CAN-SPAM footer/List-Unsubscribe header — those are exempt per §12.

- 2026-07-04 — `settings.business_mailing_address` defaults to an empty string with a `TODO(jorge-verify)` marker (`crm/src/settings/defaults.ts`). CAN-SPAM requires a real physical mailing address in commercial email footers; this repo has no such address configured anywhere. `buildCanSpamFooter` renders a clearly-labeled placeholder line when it's empty rather than fabricating one. **Action for Jorge before any real campaign send:** `PUT /api/settings/business_mailing_address` with the real address.

- 2026-07-04 — `npm run setup:gmail` is a standalone interactive CLI (not a route on the running server) that spins up its own temporary loopback HTTP listener on `GOOGLE_REDIRECT_URI`'s port to catch the OAuth redirect, exchanges the code, and writes `GMAIL_REFRESH_TOKEN`/`GMAIL_FROM`/`GMAIL_HISTORY_ID` into `crm/.env` directly (via a small pure `upsertEnvVar` helper, tested in isolation). It requests `prompt: 'consent'` so a refresh token is issued even if this Google account previously granted the app access (Google otherwise silently omits `refresh_token` on repeat consent).
